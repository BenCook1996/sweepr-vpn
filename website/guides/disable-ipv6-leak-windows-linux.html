1. How Dual-Stack SLAAC, DHCPv6 & Teredo Bypass IPv4-Only VPNs

Modern UK and European broadband lines (BT, Sky, Virgin Media, Hyperoptic, Comcast) provision a native global IPv6 prefix alongside IPv4. Under RFC 8305 (Happy Eyeballs), browsers and OS networking libraries race IPv6 AAAA sockets ahead of IPv4 A connections. When a legacy VPN configuration sets only AllowedIPs = 0.0.0.0/0, your operating system cheerfully routes IPv4 traffic inside the tunnel while sending IPv6 packets straight out through your physical NIC to your ISP's router.

Even on IPv4-only routers, Windows transition protocols like Teredo (2001::/32) and 6to4 can encapsulate IPv6 over UDP port 3544 unless explicitly controlled, while spoofed or rogue ICMPv6 Router Advertisements (Type 134) on shared Wi-Fi can silently assign new default gateways.

2. WireGuard Dual-Stack Tunneling & IPv6 Blackholing (AllowedIPs = 0.0.0.0/0, ::/0)

The cleanest remediation is forcing every IPv6 packet into the encrypted WireGuard interface—either routing it cleanly through an IPv6-enabled exit server or blackholing/dropping non-tunnel ::/0 egress in the firewall:

# /etc/wireguard/wg0.conf — Enforce Dual-Stack Tunneling + Firewall Kill-Switch
[Interface]
PrivateKey = <CLIENT_PRIVATE_KEY>
Address = 10.66.12.8/32, fd00:66::12:8/128
DNS = 10.66.0.1
PostUp = nft add table inet wgkill; nft add chain inet wgkill output '{ type filter hook output priority 0; policy accept; }'; nft add rule inet wgkill output oifname != "%i" ip6 daddr != fe80::/10 ip6 daddr != ::1 drop
PostDown = nft delete table inet wgkill

[Peer]
PublicKey = <SERVER_PUBLIC_KEY>
Endpoint = 78.141.205.68:51820
AllowedIPs = 0.0.0.0/0, ::/0

Because WireGuard creates separate policy routing tables for both address families when ::/0 appears in AllowedIPs, no application socket can silently fall back to your ISP's physical WAN gateway.

3. OS Hardening: Linux sysctl, Windows PowerShell & RA Guard Verification

When administering servers, headless containers, or locked-down Windows laptops where IPv6 is unwanted outside the tunnel, disable host IPv6 bindings directly and verify Router Advertisement (RA) handling:

# --- Linux (Runtime + Persistent sysctl) ---
sudo sysctl -w net.ipv6.conf.all.disable_ipv6=1
sudo sysctl -w net.ipv6.conf.default.disable_ipv6=1
sudo sysctl -w net.ipv6.conf.lo.disable_ipv6=1
# Verify zero global unicast (2000::/3) routes remain:
ip -6 route show
# RA Guard check (confirm router/switch drops rogue ICMPv6 type 134 RA frames):
sudo tcpdump -i eth0 -n "icmp6 && ip6[40] == 134" -c 5

# --- Windows 11 PowerShell (Run as Administrator) ---
Get-NetAdapterBinding -ComponentID ms_tcpip6
Disable-NetAdapterBinding -Name "Wi-Fi" -ComponentID ms_tcpip6
Disable-NetAdapterBinding -Name "Ethernet" -ComponentID ms_tcpip6
netsh interface teredo set state disabled

Frequently Asked Questions

Is it better to disable IPv6 via sysctl / PowerShell or tunnel ::/0 through WireGuard?

Tunneling ::/0 through WireGuard with a strict kill-switch preserves compatibility with IPv6-only developer endpoints while preventing leaks. Disabling IPv6 via sysctl or ms_tcpip6 is useful as an extra host defense when managing IPv4-only VPN profiles.

Why do I still see fe80:: addresses after adjusting Windows adapter bindings?

Addresses starting with fe80::/10 are non-routable link-local identifiers used only on your local Ethernet/Wi-Fi segment (similar to 169.254.x.x). Only global unicast addresses (typically starting with 2xxx: or 3xxx:) route across the public internet.

How do I confirm zero IPv6 traffic escapes my tunnel?
