1. PMTU Blackhole Math: 1500 Ethernet vs. 1492 PPPoE vs. 5G CGNAT

WireGuard wraps every inner packet inside an outer IP header (20 bytes IPv4 or 40 bytes IPv6), an 8-byte UDP header, and 32 bytes of WireGuard protocol framing and Poly1305 authentication tag—totalling 60 bytes over IPv4 and 80 bytes over IPv6. Using the conservative 80-byte worst-case budget prevents fragmentation regardless of whether your endpoint connects over IPv4 or IPv6.

On a standard 1500-byte DOCSIS/Ethernet WAN, 1500 - 80 = 1420. However, UK Openreach PPPoE broadband (BT, Sky, TalkTalk, Plusnet, Zen) inserts an 8-byte PPPoE header, shrinking WAN MTU to 1492 bytes. Leaving WireGuard at 1420 creates 1500-byte outer frames that get silently dropped by upstream carrier routers filtering ICMP Fragmentation Needed notices—resulting in classic PMTU blackholes where small ICMP pings pass while large HTTPS certificates and SSH transfers hang.

  • Standard Ethernet / DHCP FTTP (1500 WAN MTU): 1500 - 80 = MTU 1420
  • UK Openreach PPPoE Fibre (1492 WAN MTU): 1492 - 80 = MTU 1412
  • 5G Broadband / LTE CGNAT / Starlink (1440–1460 Path MTU): MTU 1380

2. Finding Your Exact Path Ceiling With Don't-Fragment Ping Tests

Before locking your router's configuration, verify the maximum unfragmented ICMP payload that clears your broadband path. Remember that ICMP adds 28 bytes (20B IPv4 + 8B ICMP) on top of your specified payload size:

# Linux / macOS — Test 1412-byte total packet (1384 payload + 28 header = 1412)
ping -M do -s 1384 10.66.0.1
# If "Message too long" or 100% loss appears, test 1380 MTU (1352 + 28 = 1380):
ping -M do -s 1352 10.66.0.1

# Windows Command Prompt — Equivalent Don't-Fragment (-f) payload test
ping -f -l 1384 10.66.0.1
# Step down -l by 8 bytes (1376, 1368, 1352) until zero "needs to be fragmented" errors occur

3. Applying WireGuard MTU & Router TCP MSS Clamping (iptables / nftables)

After setting the interface MTU inside your .conf file, apply TCP Maximum Segment Size (MSS) clamping on Linux or OpenWrt gateways so remote HTTPS servers automatically shrink TCP segments to fit inside the encrypted tunnel:

# WireGuard client [Interface] configuration (PPPoE Fibre example)
[Interface]
MTU = 1412
Address = 10.66.12.8/32
DNS = 10.66.0.1

# Legacy iptables mangle MSS clamp (set 1340 for 1380 MTU or clamp automatically to PMTU)
iptables -t mangle -A FORWARD -o wg0 -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu
iptables -t mangle -A FORWARD -i wg0 -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu

# Modern nftables equivalent (OpenWrt 23.05+ / Debian 12+)
nft add rule inet fw4 forward oifname "wg0" tcp flags syn / syn,rst tcp option maxseg size set rt mtu
nft add rule inet fw4 forward iifname "wg0" tcp flags syn / syn,rst tcp option maxseg size set rt mtu

Frequently Asked Questions

Why do small ICMP pings succeed on PPPoE when TLS websites and SSH sessions freeze?

Standard 64-byte ICMP echo packets easily fit inside a 1492-byte PPPoE frame even with 80 bytes of WireGuard overhead. Large TLS ServerHello certificates and SSH key exchanges hit 1420+ bytes, exceed the PPPoE ceiling, and get dropped silently if carrier routers block ICMP Type 3 Code 4 Path MTU signals.

Why subtract 80 bytes instead of 60 bytes when calculating WireGuard MTU?

WireGuard adds 60 bytes of overhead over an IPv4 outer endpoint and 80 bytes over an IPv6 outer endpoint. Always subtracting 80 bytes guarantees zero outer fragmentation even when roaming between IPv4 Wi-Fi and IPv6 mobile networks.

Is setting MTU = 1412 enough without adding TCP MSS clamping?

Local host apps honour the interface MTU directly, whereas LAN devices sitting behind a WireGuard router (phones, consoles, Smart TVs) advertise a 1460-byte MSS unless the router rewrites SYN headers with TCPMSS --clamp-mss-to-pmtu.
