1. Why Windows 11 SMHNR & Automatic DoH Leak DNS Queries

By default, Windows 11's Dnscache service executes Smart Multi-Homed Name Resolution (SMHNR): whenever multiple interfaces exist (Wi-Fi, Ethernet, virtual Hyper-V switches, and a WireGuard adapter), Windows dispatches parallel DNS requests to every interface's configured resolver and caches whichever reply arrives first. Because your home ISP router sits less than 1 millisecond away on LAN, it consistently beats a remote VPN resolver unless explicitly suppressed.

A second leak vector is Encrypted DNS-over-HTTPS (DoH) fallback. Windows 11's EnableAutoDoh feature and Chromium/Edge Use secure DNS settings can silently promote queries to port 443 endpoints (dns.google or cloudflare-dns.com), bypassing adapter-level UDP port 53 rules and disclosing browsing metadata to third-party resolvers outside your VPN's private resolver.

2. Inspecting NRPT Policies & Disabling SMHNR via PowerShell

Open an elevated PowerShell prompt to audit existing Name Resolution Policy Table (NRPT) bindings, disable multi-homed DNS racing, turn off unrequested automatic DoH upgrades, and purge cached ISP entries:

# 1. Inspect current NRPT rules and per-adapter DNS servers
Get-DnsClientNrptRule
Get-DnsClientServerAddress -AddressFamily IPv4

# 2. Disable Smart Multi-Homed Name Resolution (SMHNR) via Group Policy registry key
reg add "HKLM\SOFTWARE\Policies\Microsoft\Windows NT\DNSClient" /v DisableSmartNameResolution /t REG_DWORD /d 1 /f

# 3. Disable opportunistic OS DoH auto-upgrade outside tunnel DNS
reg add "HKLM\SYSTEM\CurrentControlSet\Services\Dnscache\Parameters" /v EnableAutoDoh /t REG_DWORD /d 0 /f

# 4. Flush Windows resolver cache immediately after tunnel activation
ipconfig /flushdns
Clear-DnsClientCache

If using Microsoft Edge or Google Chrome, also set Use secure DNS to Off inside browser privacy settings so browsers follow the operating system's WireGuard-bound resolver (10.64.0.1) rather than opening direct HTTPS resolver sockets.

3. WireGuard BlockDNS & Windows Firewall Port 53/853 Rules

Even with SMHNR disabled, WireGuard for Windows and SWEEPR's Windows WFP kill-switch enforce kernel-level firewall filters (known internally as BlockDNS when DNS = 10.64.0.1 is specified). These Windows Filtering Platform (WFP) rules block all outbound UDP/TCP port 53 and DNS-over-TLS port 853 packets on non-tunnel adapters while permitting traffic solely to 10.64.0.1 inside the tunnel:

# Manual Windows Defender Firewall fallback blocking non-tunnel DNS (UDP/TCP 53 & DoT 853)
New-NetFirewallRule -DisplayName "Block Non-Tunnel DNS 53" -Direction Outbound -Action Block -Protocol UDP -RemotePort 53 -InterfaceType Wireless,Wired
New-NetFirewallRule -DisplayName "Block Non-Tunnel DNS TCP 53" -Direction Outbound -Action Block -Protocol TCP -RemotePort 53 -InterfaceType Wireless,Wired
New-NetFirewallRule -DisplayName "Block Non-Tunnel DoT 853" -Direction Outbound -Action Block -Protocol TCP -RemotePort 853 -InterfaceType Wireless,Wired
